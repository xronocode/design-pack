# Память вкуса проекта

Дизайн-решения, не записанные в файл, умирают вместе с сессией. Этот скил держит два артефакта в корне проекта:

- **`DESIGN.md`** — текущая дизайн-система проекта: направление, токены, компоненты, голос.
- **`appearance-ledger.md`** — журнал решений: почему выглядит именно так, что пробовали и отвергли.

## Когда что делать

| Ситуация | Действие |
|---|---|
| Начало нового проекта / первый дизайн-запрос | Создай оба файла по шаблонам ниже (после `direction`) |
| Перед любой дизайн-работой | Прочитай `DESIGN.md` целиком; если его нет — предложи создать, а не выдумывай стиль с нуля |
| После `direction` / `restyle` / смены токенов | Обнови `DESIGN.md`; старую версию направления — в ledger со статусом «заменено» |
| Принял нетривиальное решение вкуса | Допиши запись в ledger (формат ниже) |
| Пользователь поправил твой дизайн | Обязательно запись в ledger с пометкой `source: user` — это самые ценные данные |
| Дизайн «разъехался» между фичами | Аудит кода против `DESIGN.md`, вернуть токены, расхождения — в ledger |

## Шаблон `DESIGN.md`

```markdown
# DESIGN — <проект>

Обновлено: YYYY-MM-DD · Стиль: <slug из библиотеки или описание>

## Контекст
Продукт: <что и для кого> · Носители: <web/mobile/deck/…> · Настроение: <3–5 слов>

## Направление
База: <slug> (+ гибриды, если есть). Суть решения — 2–3 предложения: почему именно это.

## Токены
- Палитра: bg / surface / text / muted / accent (+ hex и роли; dark-вариант, если есть)
- Типографика: display (семейство, веса) / body / data; scale в rem; межстрочные
- Сетка и spacing: шкала, контейнер, мерная колонка
- Радиусы / тени / границы: шкалы и правила применения
- Моушн: длительности, easing, где допустимо/запрещено

## Компоненты
- Кнопки: варианты, состояния, размеры
- Карточки/панели: когда используются, чего внутри быть не может
- Формы и таблицы: правила
- Иконки: набор, вес, размеры

## Голос
Тон текста интерфейса: <обращение, длина, канонические формулировки>

## Референсы
Нравится: <ссылки/скрины и что именно в них работает>
Анти-референсы: <чего не должно быть ни при каких условиях>
```

## Шаблон `appearance-ledger.md`

```markdown
# Appearance ledger — <проект>

Формат записи (новые — сверху):

## YYYY-MM-DD — <короткое название решения>
- Решение: <что принято>
- Почему: <аргумент / контекст>
- Альтернативы: <что отвергли и за что>
- Источник: direction | audit | polish | user | constraint
- Артефакт: <файл/скрин, если есть>
```

## Правила

1. Ledger пишется прозой и аргументами, а не «поменял цвет». Через месяц должно быть понятно, почему.
2. Никогда не удаляй отвергнутые альтернативы — они защищают от повторного спора.
3. `DESIGN.md` всегда отражает только текущее состояние; история живёт в ledger.
4. Если проект чужой и в нём есть свой дизайн-система (style guide, theme-файл) — не создавай параллельную: изучи существующую и при необходимости составь `DESIGN.md` как её выжимку.
5. Конфликт «токены DESIGN.md ↔ код»: код неправ. Исключение — сознательное решение пользователя, тогда обновляются токены.
